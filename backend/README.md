# Re:hear backend candidate

Standalone code candidate copied from the existing sushi-fast ODI, shared auth and rehear_ai code. No operational cutover has been performed. Do not point production traffic at this candidate yet.

`main:app` exposes the existing `/odi` and `/auth` routes. The candidate deliberately does not initialize or migrate databases at import/startup. A fresh isolated database is needed for local operation; use test fixtures for synthetic testing. AI, JWT, email and other configuration is intentionally not copied. See `requirements.txt` and the EVC requirements files for dependencies. Google OAuth is owned by the existing Sushisite authentication service; it is intentionally not copied into this candidate. Other Sushi services are deliberately excluded.

## Authentication routing candidate

`Caddyfile` is a loopback-only example, not an operational ingress configuration: send `/auth` and `/auth/*` unchanged to the existing Sushisite service; route the `/odi/db`, `/odi/files`, `/odi/coaching`, and `/odi/xreal_rehear` API namespaces and descendants unchanged to this backend; route screens such as `/odi` and `/odi/login` and other paths to the frontend. Keep the namespace list aligned with the frontend's `scripts/hosting-proxy.mjs` and backend routes. Configure `LISTEN_PORT`, `LEGACY_AUTH_UPSTREAM`, `REHEAR_BACKEND_UPSTREAM`, and `FRONTEND_UPSTREAM` for an isolated environment; none has an operational default. The real TLS ingress must remain separate and trusted, preserve the original public Host, path and query on both Google start and callback, and keep both requests on the same original auth service/state store. Do not expose the example listener. Do not log authorization queries, authentication headers or session data.

Existing OAuth derives its callback host from the incoming host and allows only configured hosts; registered Google redirect URIs must already match. The legacy service must retain its own auth database and configuration. ODI login/join also validates the existing primary identity and reads the ODI user database: compatible signing configuration and identity mapping, existing ODI data/media, and lifecycle/startup must be confirmed before any cutover, without copying or exposing secrets here. The loopback test uses a simulated legacy server and tests routing and error-return only; it does not prove a real Google exchange, session establishment, cookie attributes, JWT interoperability, frontend login or production ingress behavior.

Keeping Quest's existing URL requires retaining the public host, TLS ingress/reverse-proxy mapping, request paths and methods. Copying code does not change where traffic goes. The current database path is relative to `odi/db/odidb.py` and media is relative to the application root, so launching from this folder will not automatically use the original data. Original startup also initializes/migrates the ODI schema and recovers interrupted jobs; this candidate deliberately omits those operations. Any eventual cutover requires separate validation of startup, runtime configuration, existing auth/data/storage, CORS, migrations and live compatibility, and explicit operational approval; do not migrate the production database or restart the service as part of this candidate.

## Quest compatibility notes

The existing EVC session store is in process memory: restarting or routing an in-progress session to another worker loses access to it. Preserve the existing single-worker/sticky-session behavior until a shared store has been designed and verified. Independent audience reactions are opt-in; keep the existing default rather than forcing them on. For an eventual cutover preserve multipart/JSON/audio formats, EVC session header, request IDs, step guards and client-time behavior, as well as the public host and ingress mapping. The Unity source and actual deployed Quest configuration were not available for this verification.

## Local validation performed

The ingress integration suite `tests/test_ingress_contract.py` runs the actual frontend candidate (Vite), actual backend candidate (Uvicorn), Caddy, and a simulated legacy authentication server on loopback, with an isolated frontend database path and synthetic configuration. It covers `/odi?x=1` screen redirection, simulated Google error return through that screen to HTML, API namespace coverage against the backend OpenAPI paths, and Quest smart-start/read/update routing with missing-input/auth errors. The Google provider and legacy authentication implementation are not exercised. The frontend must have its dependencies installed and must not contain `.env*` files when this suite runs. Run with `TMPDIR` pointing to a scratch directory and `pytest tests/test_ingress_contract.py -q`; no production environment or data should be supplied.

With the original project's Python environment, 91 synthetic EVC and practice-run tests passed, including the Quest smart-start/read/update HTTP test with stubbed providers. The candidate's `/odi` and `/auth` OpenAPI schema was identical to the current source routers (64 paths); a loopback Uvicorn process served `/openapi.json` successfully and was stopped. This does not verify deployed ingress, actual Quest, external AI/STT/TTS, Google login, production auth or storage.

Existing incident tests are not all compatible with the current source: 8 failed and 1 passed on both the source and candidate. They concern a separate, incomplete My Practice incident/scenario workstream; do not assume that feature is ready here. Some tests create a local `odi/db/odi.db`; treat it as test data and keep it out of Git. Fresh dependency installation has not been verified.
